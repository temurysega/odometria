# Анализ предоставленного датасета

Исходные файлы: `условия/dataset.zip` и PDF «Резервная одометрия по модели». Архив содержит вложенный `data.zip`, `README.md` и пакет `tram_vehicle_msgs`. `data.zip` распакован локально в `условия/dataset/data`; сырые bag не входят в этот репозиторий. Полная машинная сводка каждого прогона находится в `reports/bag_analysis.json`.

## Объём и схема

122 каталога rosbag2 SQLite, из них 103 с префиксом `30618` и 19 с префиксом `30639`. Суммарно 8 788 325 сообщений за 36,75 часа, медианная длительность прогона 19,85 минуты. Для каждого прогона доступны две скорости тележек и позиция контроллера. Типы — `tram_vehicle_msgs/msg/VelocitySensor` и `tram_vehicle_msgs/msg/DriverControllerCommand`. Позиция контроллера лежит в пределах −15…+15.

GNSS существует не во всех записях: в 35 bag нет ни одного сообщения GNSS скорости. В 86 записях анализатор сравнивает с `/sensing/gnss/master/vel`, ещё в одной — с `/sensing/gnss/rover/vel`. GNSS используется только в `tools/analyze_dataset.py` для метрик; рабочий узел подписывается исключительно на три разрешённых `/vehicle/*` топика.

## Обнаруженные особенности

1. Хотя README архива помечает `VelocitySensor.velocity` как м/с, значения в bag численно соответствуют **км/ч**. Например, на `30618_01f73500` медианная скорость передней тележки 12,29, а GNSS 3,48 м/с; максимальные значения 53,28 и 14,84 м/с. Перевод колёс на `1/3.6` снизил RMSE на этом прогоне с 8,68 до примерно 0,031 м/с. Масштаб открыт параметром `wheel_speed_scale`.
2. `header.stamp` разных `/vehicle/*` топиков на начальном участке записи имеет разные смещения относительно времени SQLite. На `30618_0d865417` начальные смещения: задняя тележка −3,42 с, передняя −2,33 с, контроллер −2,42 с. Они меняются в ходе прогона. Поэтому простое сравнение заголовков для синхронизации отбросило бы значительную долю данных. Офлайн анализатор использует время записи SQLite; ROS узел использует монотонное время получения.
3. На `30618_01f73500` найдено 23 365 событий колёс за 1 211,98 с, то есть суммарно около 19,3 Гц. Публикация при каждом событии тележки даёт требуемый порядок частоты вывода.

Метрики анализатора сравнивают скорость с модулем вектора GNSS при ближайшем времени записи в пределах 0,05 с. Это офлайн оценка на предоставленных данных, а не результат запуска ROS 2 на стенде. Оценка трёхмерного положения пока не реализована: текущий `Odometry.position.x` — расстояние вдоль пути от начальной точки; для глобальных `x/y/z` потребуется карта маршрута и ориентация/начальная привязка.

На 87 записях с GNSS получено 1 677 162 сопоставленных отсчёта: суммарный RMSE скорости 0,131 м/с, медианный RMSE по записи 0,036 м/с. Наихудший RMSE отдельной записи 0,670 м/с. Эти числа относятся к офлайн воспроизведению по времени записи SQLite и не измеряют задержку публикации ROS узла.

Временные метки выходов можно проверить отдельно командой `python tools/check_timestamps.py /path/to/bag`. На `30618_01f73500` при допуске 0,05 с с заголовками master GNSS совпали 11 452 из 11 694 публикаций передней тележки и 11 429 из 11 671 публикаций задней. На `30639_e4379d7f`, где есть только rover GNSS, совпало около 40% публикаций: rover и входные заголовки имеют разные часы. Для судьи, который сверяет именно `header.stamp`, этот случай требует отдельной калибровки времени в ROS среде.
